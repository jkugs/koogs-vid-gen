# AI Video Project — Iteration 1

## Goal

Build the smallest possible end-to-end image-to-video generation workflow using an open-source video model running on rented GPU compute.

The purpose of this iteration is **not** to build the AI filmmaking application yet.

The purpose is to prove that we can:

1. Run an open-source image-to-video model ourselves.
2. Provide a real photograph as the starting image.
3. Provide a text prompt describing motion/action.
4. Generate a short video.
5. Save the result as a standard MP4.
6. Evaluate how well the model preserves the person's identity.

This iteration should remain deliberately small and experimental.

---

## Long-Term Context

The eventual goal is to build a personal AI filmmaking system capable of creating videos featuring consistent real people/characters.

A future workflow may look roughly like:

```text
Character Reference Images
        ↓
Identity-Preserving Image Generation
        ↓
Generated Scene / Keyframe
        ↓
Image-to-Video Generation
        ↓
Identity / Face Refinement
        ↓
Video Clip
        ↓
Editing / Sequencing
        ↓
Movie
```

The application may eventually support concepts such as:

* Characters
* Multiple reference images per character
* Identity-preserving image generation
* LoRA training
* Image-to-video generation
* Character animation
* Face/identity correction
* Upscaling
* Lip synchronization
* Voice generation/cloning
* Scenes and shots
* Projects
* Clip sequencing
* GPU job orchestration
* A web UI

**None of those systems need to be built during Iteration 1.**

# Iteration 1 Scope

Iteration 1 consists of a single Python image-to-video generation script.

Conceptually:

```text
input.jpg
    +
text prompt
    ↓
generate_video.py
    ↓
output.mp4
```

The initial implementation should favor simplicity and understandability over abstraction.

---

## Input

The script should accept or initially hardcode:

### Input Image

A local image containing the person/subject to animate.

Example:

```text
input.jpg
```

### Prompt

A text description of what should happen in the generated video.

Example:

```text
The person slowly turns their head toward the camera and smiles.
The camera remains stationary.
Natural movement, realistic lighting.
```

For the first implementation, hardcoded values are acceptable.

CLI arguments can be added if doing so remains trivial.

---

## Output

The script should generate:

```text
output.mp4
```

The output should be a short video clip derived from the supplied image and prompt.

We are initially targeting approximately **5 seconds** of video.

Exact duration, FPS, resolution, and inference parameters should follow reasonable defaults for the selected model rather than introducing unnecessary configuration.

---

# Model

The initial model should be an **open-source image-to-video model** that can be run directly on rented GPU infrastructure.

Wan 2.2 is currently the leading candidate, but the implementation should be based on the specific model/version selected during setup.

Do not build a generic multi-model framework during this iteration.

It is acceptable for the first implementation to be tightly coupled to the selected model.

We want to understand the model before abstracting it.

---

# Compute Environment

Development code will live in this Git repository.

GPU inference will initially run on a rented **RunPod GPU Pod**.

The intended workflow is approximately:

```text
Local Development
       ↓
GitHub
       ↓
RunPod GPU Pod
       ↓
git clone / git pull
       ↓
uv sync
       ↓
python generate_video.py
       ↓
output.mp4
```

A normal interactive GPU Pod should be used during early experimentation.

Do **not** build RunPod Serverless integration yet.

Serverless/job orchestration can be introduced later after the inference workflow is understood and stable.

---

# Python Environment

The project uses **uv** for Python dependency and environment management.

Dependencies should therefore be managed through the existing uv project configuration rather than introducing a second environment-management mechanism.

Prefer:

```bash
uv add <dependency>
```

and:

```bash
uv run python generate_video.py
```

where appropriate.

Avoid adding Docker unless the selected model or RunPod environment makes it necessary.

# Implementation Responsibilities

`generate_video.py` should perform the minimum operations necessary to generate the clip.

Conceptually:

```python
image = load_image("inputs/input.jpg")

model = load_model()

frames = model.generate(
    image=image,
    prompt=PROMPT,
)

save_video(
    frames,
    "outputs/output.mp4",
)
```

The actual implementation will depend on the selected model's inference API.

---

# Basic Observability

The script should print enough information to make experimentation useful.

At minimum, report:

* Selected model
* GPU being used
* Input image
* Output path
* Generation parameters that materially affect the result
* Model loading time
* Generation/inference time
* Total execution time

If easily available, also report:

* GPU VRAM usage
* Peak GPU VRAM usage

Do not introduce a full logging framework unless one is genuinely useful.

Simple readable console output is sufficient.

# What We Are Testing

Iteration 1 is an experiment.

The important output isn't merely `output.mp4`.

We want to answer several questions.

### 1. Can we reliably run the model ourselves?

We should understand:

* installation
* model downloading
* GPU requirements
* inference process
* output encoding

### 2. What does generation cost?

Record approximately:

* GPU type
* VRAM
* generation time
* clip duration
* resolution

This will eventually help estimate per-shot generation cost.

### 3. How well does image-to-video preserve identity?

This is the most important creative experiment.

Given a recognizable person in the source photograph:

> Does the generated person still clearly look like the same person?

We specifically want to observe identity degradation during things such as:

* head movement
* facial expressions
* body movement
* camera movement
* profile views
* lighting changes

### 4. What are the model's failure modes?

Examples might include:

* facial drift
* distorted hands
* changing clothing
* changing hair
* unnatural movement
* background instability
* subject duplication
* temporal artifacts

These observations will inform later architecture.

# Test Strategy

Once basic generation works, run several controlled experiments using the same input image.

For example:

### Test A — Minimal Motion

```text
The person looks toward the camera and smiles slightly.
The camera remains stationary.
```

### Test B — Head Movement

```text
The person slowly turns their head to the side and looks away from the camera.
```

### Test C — Body Movement

```text
The person stands up and begins walking slowly toward the camera.
```

### Test D — Camera Movement

```text
The person remains still while the camera slowly moves around them.
```

The exact prompts can change.

The important thing is to gradually increase motion complexity and observe where identity or temporal consistency begins to fail.

# Engineering Philosophy

This project will likely evolve quickly because generative video models are changing quickly.

Therefore:

**Learn first. Abstract second.**

Avoid designing generalized interfaces around workflows we do not yet understand.

For Iteration 1:

* Prefer explicit code.
* Prefer few dependencies.
* Prefer simple scripts.
* Prefer direct model APIs.
* Prefer experimentation over architecture.
* Avoid speculative abstractions.

Once several models and workflows have actually been used, common abstractions should become much more obvious.

---

# Definition of Done

Iteration 1 is complete when we can execute something equivalent to:

```bash
uv run python generate_video.py
```

on a RunPod GPU and reliably produce:

```text
outputs/output.mp4
```

from:

```text
inputs/input.jpg
```

and a text prompt.

The resulting video does not need to be perfect.

At completion we should understand:

1. How to run the selected model.
2. What GPU resources it requires.
3. Rough generation time and cost.
4. How good the generated motion looks.
5. How well a real person's identity survives generation.
6. The most obvious failure modes.

Those findings will determine Iteration 2 rather than assuming its architecture in advance.
